# Skill: Write PRD

> 编写结构化的产品需求文档（PRD），包含背景、目标、用户故事和验收标准，为后续开发提供明确方向。

## 触发时机

- 收到 product-design 角色的任务
- 需要将产品需求结构化输出时
- 需要把口头需求转化为可开发的文档时

## 前置条件

- 已通过 `claim-task` 认领 product-design 任务
- 已阅读相关 README、`docs/` 目录、相关 issue 讨论
- 已知目标用户的角色与核心使用场景

## 工作流程

### 1. 阅读项目背景

```bash
# 阅读项目结构
ls docs/
cat README.md

# 阅读相关代码或已有需求
rg "feature|requirement" docs/ -l
```

### 2. 编写 PRD 文档结构

PRD 输出到 `docs/requirements/<feature-name>.md`，使用以下结构：

```markdown
# <功能名称>

## 背景
<业务背景、问题描述、为什么需要这个功能>

## 目标
<业务目标（可衡量）、非目标（明确范围之外）>

## 用户故事
- 作为 <用户角色>，我希望 <功能>，以便 <价值>
- 作为 <用户角色>，我希望 <功能>，以便 <价值>
- ...

## 验收标准
- [ ] 标准 1：<具体、可验证的条件>
- [ ] 标准 2：<具体、可验证的条件>
- [ ] 标准 3：<边界情况处理>
- [ ] ...

## 技术约束
<API 兼容性、性能要求、依赖说明>

## 风险与开放问题
<已识别的风险、待确认的决策点>
```

### 3. 用户故事覆盖

至少覆盖：
- **正常流程**：用户成功完成操作的路径
- **边界情况**：空数据、超大数据量、并发操作
- **异常处理**：网络错误、权限不足、状态不一致

### 4. 验收标准可测试

每条验收标准必须满足：
- ✅ 可被开发团队直接用于编写测试
- ✅ 不使用模糊描述（避免"良好体验"、"合理性能"）
- ✅ 包含具体输入/输出/状态

### 5. 引用任务编号

在 PRD 中引用对应的 Kaneo 任务编号（如 `KIA-123`），并在「关联任务」部分列出。

## 关键约束

- **不要直接修改源代码**（.ts/.tsx/.py/.go 等实现文件）
- **不要运行测试或构建命令**
- **不要创建包含代码变更的 PR**（仅文档变更可提交 PR）
- **不要修改数据库 schema 或 API 路由**
- 文档使用中文描述，技术术语保留英文

## 质量标准

- 文档结构清晰：背景、目标、用户故事、验收标准、约束、风险
- 用户故事覆盖正常流程 + 边界情况 + 异常处理
- 验收标准可被开发团队直接用于编写测试用例
- 关联到具体 Kaneo 任务编号

## 完成后

1. 确认 PRD 文件已保存到 `docs/requirements/<feature-name>.md`
2. 如果需求拆分为多个开发任务，使用 `claim-task` skill 创建子任务并设置对应的 `requiredRole`（如 `coding`、`ui-design`）
3. 调用 `PUT /api/task/status/{taskId}` 将任务状态更新为 `in-review`
4. 提交仅包含文档变更的 PR（通过 `submit-pr` 已被禁止，但可在评论中说明文档位置）
