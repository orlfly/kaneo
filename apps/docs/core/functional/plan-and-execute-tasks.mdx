---
title: Plan and Execute Tasks in Board and List
description: Create tasks, set metadata, and execute work using Board and List views
---

Use this workflow to move from planning to execution with minimal overhead.

## 1. Create tasks quickly

In a project:

1. Open **Board** or **List** view.
2. Click **Create task**.
3. Add a short, action-oriented title.
4. Optionally set description, assignee, priority, due date, and labels.

## 2. Keep task data clean

When editing tasks, prioritize:

- Clear scope in the description
- One owner (assignee)
- Explicit priority
- Realistic due dates
- Reusable labels

## 3. Execute in Board view

Board view is best for flow-based execution:

1. Pull tasks into active columns.
2. Drag tasks across columns as status changes.
3. Open a task to edit details without losing board context.

## 4. Switch to List view for dense review

List view is useful when you need to scan many tasks quickly.

Typical uses:

- Reviewing priorities across the project
- Spotting overdue work
- Finding unassigned or under-specified tasks

## 5. Use filters to focus

The board toolbar supports filtering by:

- Status
- Priority
- Assignee
- Due date
- Labels

Use filters aggressively during standups, planning, and triage.

## 6. Open full task page when needed

From the task sheet, use **Open in full page** for deeper edits and focused context.

## 7. Read dependencies on the Gantt view

The project's **Gantt** tab places every scheduled task on a timeline. A task needs a start date, a due date, or both to appear; tasks without any dates stay in the backlog.

Task relations show up here:

- A `blocks` relation is drawn as a connector from the blocker's end into the task it blocks, with an arrow head at the blocked task. The blocked bar also carries a **Blocked by …** badge, so the blocker is still identifiable when its bar is scrolled out of the window.
- The connector turns red when the blocked task is scheduled to start before its blocker is due. Move the blocked task's start date on or after the blocker's due date to clear it.
- `subtask` and `related` relations are not drawn on the timeline; they live in the task page's **Relations** and **Subtasks** sections.

Declare the relation when you create the task, or link it later from the task page. Agents do the same when they discover a prerequisite or a follow-up: create the task and its relation together.

## 8. Dependencies gate what agents are handed

A `blocks` relation is enforced, not advisory. While a blocker is outside a final column:

- **Agent dispatch skips the blocked task.** `claim-next` never returns it, so an agent is not handed work it cannot start. Once the blocker reaches a final column, or is archived, the task becomes claimable again with no manual step.
- **An explicit claim is refused** with `409` naming the blocking tasks, so a caller learns why instead of starting blocked work.
- `subtask` and `related` relations never gate dispatch; only `blocks` does.

Agents see the dependency picture without extra calls: the project context bundle carries `dependencies` with `blockedBy` and `blocks`, and the same information is written into `KANEO_CONTEXT.md`. An agent that discovers a prerequisite mid-task creates it with a `blocks` relation and pauses its own task, naming the blocker in the pause reason; it does not pick up the prerequisite itself. Completing a task unblocks everything it pointed at.
